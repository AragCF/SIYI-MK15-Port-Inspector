# Разбор четырёх реальных отчётов MK15 Port Inspector 1.3.0

Дата анализа: 2026-09-23.

Исходные отчёты:
- MK15_Report_20260923_054536_v1_3_0.zip
- MK15_Report_20260923_054541_v1_3_0.zip
- MK15_Report_20260923_054617_v1_3_0.zip
- MK15_Report_20260923_054953_v1_3_0.zip

## 1. Что подтверждено

Версия 1.3.0 установлена и работает на реальном QUALCOMM MK15 / Android 9.

Автономный канал передачи отчётов работает:
- ZIP формируется на пульте;
- сохранение через Android file picker работает;
- отправка в thesystem возвращала HTTP 200.

Встроенный CP2102 обнаружен Android USB Host:
- VID=10C4
- PID=EA60
- Android USB permission выдано;
- порт открыт на 57600 8N1.

Все три внутренних tty доступны обычному APK:
- /dev/ttyHS0 read/write;
- /dev/ttyHS1 read/write;
- /dev/ttyHS2 read/write.

AUTO успешно открыл:
- USB CP2102;
- UDP 192.168.144.12:19856;
- UART0 /dev/ttyHS0;
- UART1 /dev/ttyHS1;
- UART2 /dev/ttyHS2.

## 2. Главный результат: SIYI SDK пока не отвечает ни по одному активному пути

Во время активного поиска приложение отправляло:
- 0x42 Request Channel Data, 20 Гц;
- 0x48 Request All Channel Mappings.

Команды действительно ушли в USB, UDP и UART0/1/2.

Однако во всех четырёх отчётах:
- transport.usb.rxBytes=0;
- transport.udp.rxBytes=0;
- transport.uart0.rxBytes=0;
- transport.uart1.rxBytes=0;
- transport.uart2.rxBytes=0;
- rc.last.source=none;
- живые CH1..CH16 отсутствуют;
- mapping 0x48 не получен.

Следовательно, источник C/D через публичный 0x42 в этих опытах ещё не достигнут.

Это не означает, что 0x42 на MK15 не работает. Официальная документация SIYI указывает, что интерфейс Datalink выбирается в приложении SIYI TX, а SDK UART использует /dev/ttyHS0 с 115200 бод. Текущая 1.3.0 открывает raw tty как обычный FileInputStream/FileOutputStream и не настраивает termios/raw/baud, поэтому результат UART нельзя считать отрицательным доказательством.

## 3. Linux input

В системе существует устройство:
- gpio-keys / event3.

Но обычному APK недоступно чтение /dev/input/event3:
- readable=false;
- writable=false.

Аналогично закрыты остальные /dev/input/event*.

В журнале нет Android KeyEvent/MotionEvent, которые можно было бы уверенно связать с C или D.

То есть обычный Android input-путь пока не дал источник C/D.

## 4. Что показал Switch Finder

В отчётах есть серии, маркированные отдельно C и D.

Полезного RC/Input кандидата в них нет, потому что живые RC-данные не пришли и Linux input закрыт.

Основной шум:
- системные IRQ;
- /sys/kernel/debug/gpio.

Особенно заметны gpio75, gpio83, gpio84 и большая группа gpio100..gpio125.

Важно: строки вида
"gpio75 : in 1 6mA pull down"
в debugfs описывают pinmux/function/drive/pull-конфигурацию, а не чистое логическое состояние кнопки 0/1.

Эти группы меняются блоками и не имеют достаточно устойчивого соответствия C/D. Их нельзя объявлять источником кнопок.

## 5. Сравнение четырёх ZIP

Первые два ZIP содержат один и тот же Finder history на 13 раундов и являются практически соседними снимками одного опыта.

Следующие два отчёта добавляют отдельные серии:
- 18 раундов;
- 11 раундов с чередованием C/D.

Самая чистая чередующаяся серия C-D-C-D не показывает стабильного уникального GPIO/IRQ-кандидата, отличающего C от D.

## 6. Что нужно исправить в следующей версии

Приоритет 1:
- настроить /dev/ttyHS0 именно как raw UART;
- установить 115200 бод для SDK UART;
- записывать результат termios/stty-настройки в ZIP.

Приоритет 2:
- не считать ttyHS1/2 подтверждёнными SIYI SDK-портами; официальный путь — ttyHS0;
- ttyHS1/2 можно оставить как пассивные исследовательские источники, но не слать туда протокол без необходимости.

Приоритет 3:
- если USB/UDP/UART0 не возвращают ни одного валидного SIYI кадра, выводить на экране явную подсказку проверить SIYI TX -> Datalink -> Connection;
- официальный SDK говорит, что коммуникационный интерфейс переключается именно в SIYI TX.

Приоритет 4:
- сохранить отдельную маркировку C/D и полный дифф, поскольку это уже работает корректно.

## 7. Текущий вывод

C и D пока не найдены.

Зато четыре отчёта исключили несколько ложных направлений и дали важную техническую развилку:
- Android Input напрямую недоступен;
- CP2102 реально открывается;
- ttyHS0 реально доступен приложению;
- исходящие SDK-команды реально отправляются;
- проблема сейчас находится между "порт открыт" и "SIYI Datalink отвечает".

Следующий рациональный эксперимент — правильно настроенный raw /dev/ttyHS0 на 115200 и проверка выбранного Datalink Connection в SIYI TX.
