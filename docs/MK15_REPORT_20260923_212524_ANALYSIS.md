# Разбор MK15_Report_20260923_212524_v1_3_4

## Факт

Версия 1.3.4 по-прежнему не получила ни одного живого `0x42`:
- `rc.channel_frame_count=0`;
- `rc.valid_siyi_frames=0`;
- UART0 получил только один 42-байтовый mapping-ответ;
- USB и UDP RX оставались нулевыми.

## Главная причина

Все команды path-based `stty -F /dev/ttyHS0 ...` вернули rc=0, но немедленный effective `stty -a` снова показал:

- `iuclc`;
- `istrip`;
- `inpck`;
- `ignpar`;
- `ixon`;
- `ixoff`;
- `ixany`;
- `icrnl`;
- `inlcr`.

Следовательно, на этом драйвере каждое новое открытие ttyHS0 получает vendor-default termios; настройка через отдельное открытие пути не управляет тем дескриптором, которым читает Java.

## Дополнительная ошибка последовательности

Журнал показал первый `0x42` ещё до строки `0x48 PRE-RC mapping`. Причина — AUTO reconnect самостоятельно запускал RC probe, а затем центральный сценарий запускал его повторно.

## Исправление 1.3.5

- `/dev/ttyHS0` теперь один раз открывается shell-процессом как fd3;
- `stty ... <&3` настраивает именно тот же открытый fd;
- fd3 остаётся открыт весь сеанс;
- stdin приложения мостится в fd3, чтение fd3 — обратно в Java parser;
- AUTO reconnect больше не запускает 0x42 самостоятельно;
- последовательность полностью централизована: mapping → пауза → 0x42.

Это следующая различающая аппаратная проверка.
